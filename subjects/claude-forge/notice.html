1.Le concept en 1 minute

Le subject pool est une infrastructure où chaque sujet de l'entreprise (commande, fournisseur, campagne, incident, vision stratégique…) est un réceptacle persistant qui accumule des intrants et matûre progressivement vers une doctrine exécutable (règle, skill auto-généré, agent SDK, monitor).

Compilation verticale

L'historique d'un même sujet dans le temps : events, analyses, discussions, décisions s'empilent. C'est le pattern /documente historique.

Compilation horizontale

Les liens entre sujets différents : order-398 ↔ supplier-weifang ↔ product-line. Chaque event sur un sujet fait vibrer ses liés. C'est ce qui distingue le subject pool d'un wiki.

★ Métaphore

Pense à une forge : tu jettes de la matière brute (events) dans le creuset (subject), tu martèles à chaque coup (re-synthèse continue), et au bout d'un certain nombre de coups + un test à chaud (stress-test), tu obtiens une épée exécutable (skill, règle, agent). Le mot "forge" désigne ce process global.

2.Architecture en 2 couches

Le moteur subject pool est séparé en deux couches qui ne se mélangent pas :

Couche 1 — Python déterministe

Fichiers : forge_engine.py, forge_lib.py, forge_scanner.py

Rôle : extraire les données structurées des sous-dossiers, calculer stats agrégées, recalculer last_event, détecter les conditions de transition γ, résoudre les liens.

Vitesse : < 500ms par subject. Pas de LLM, pas de coût.

Sortie : JSON sur stdout. Ne touche jamais aux fichiers.

Couche 2 — Claude sémantique

Skill : /documente (entry point unique)

Rôle : invoquer la couche 1 via Bash, parser le JSON, régénérer ## Quick (< 100 mots) et ## Détails (synthèse rédigée), appliquer transitions auto, propager en cascade, afficher diff, commit, push.

Vitesse : ~30s par subject (1 invocation = 1-2 subjects re-synthétisés).

Sortie : MEMORY.md modifiés + commit Git.

Pourquoi 2 couches

Le scanner Python tourne en SessionStart à chaque ouverture de session sans coût Claude — il génère la ligne Forge: ... du Health-check + les fichiers SUBJECTS-INDEX.md et SUBJECT-POOL-METRICS.md. Claude n'intervient que quand on doit re-synthétiser narrativement.

3.Anatomie d'un subject

Structure dossier

services/<X>/                      ← X = achats, ventes, marketing…
├── types/                          ← grilles partagées (REFERENCE.md + TEMPLATE.md)
│   └── <type-name>/                ex: supplier-order, marketing-campaign
│       ├── REFERENCE.md            ← grille d'analyse (analysis_dimensions, expected_events)
│       └── TEMPLATE.md             ← squelette d'instanciation
└── subjects/                       ← instances
    └── <subject-name>/             ex: order-398, supplier-weifang
        ├── MEMORY.md                ← synthèse compacte (Quick + Détails)
        ├── INDEX.md                 ← chronologique (auto-régénéré)

        ├── analyses/                ← scoring Claude sur la grille du type (optionnel)

Règle bilingue stricte

La taxonomie/squelette est en anglais (snake_case) — les champs frontmatter, les valeurs de forging_state, les noms de types. Le contenu métier reste en français — les analysis_dimensions (ex: tresorerie, delai), les expected_events (ex: alerte_stock), le contenu narratif (Quick, Détails).

4.Cycle de vie γ — les 8 états

seed → debating → tentative → stress_testing → doctrine → in_service

→ auto : transition appliquée par /documente sans intervention   → manuel : tu lances le skill correspondant

ÉtatSignificationComment y arriver
seed Signal entrant, pas encore traité État initial après /subject-create
debating En cours de raisonnement, hésitations auto dès qu'1 event ou 1 discussion ouverte
tentative Opinion formée mais pas testée auto dès qu'1 décision active (+ bump conviction à 50)
stress_testing En cours de confrontation manuel via /stress-test
doctrine Opinion solide, prête à compiler manuel après /stress-test survived (conviction +10) → seuil ≥ 60
in_service Doctrine en application, artefact compilé manuel via /compile-doctrine (requis : conviction ≥ 80)
under_review Contre-signal détecté, retour en débat manuel quand un nouvel event contredit la doctrine
archived Subject clos, leçons remontées manuel à la clôture (livraison, résolution)

Conviction (0..100)

  • Bump à 50 sur la transition debating → tentative (opinion formée a une base de confiance minimale)
  • +10 par stress-test passé (survived: true)
  • −15 par contre-signal qui force under_review
  • Seuils : ≥ 60 pour passer en doctrine, ≥ 80 pour /compile-doctrine
Math : combien de stress-tests pour compiler ?

Conviction de départ après bump = 50. Pour compiler il faut 80. Donc 3 stress-tests passés (50 + 10×3 = 80) sans contre-signal. Si un stress-test échoue, le subject redescend en debating et il faut tout reprendre.

6.Ce qui est automatique vs ce que tu fais

🤖 Ce qui se passe AUTOMATIQUEMENT

À chaque ouverture de session

  • forge_scanner.py tourne via SessionStart hook
  • Régénère entreprise/SUBJECTS-INDEX.md
  • Régénère entreprise/SUBJECT-POOL-METRICS.md
  • Affiche la ligne Forge: OK — 13 actifs, 0 stagnants… dans le Health-check
  • Émet alertes (stagnation >30j, doctrine non compilée, stress-test manquant, merger candidate)

Quand /control-tower --achats traite un email

  • Event ajouté dans subjects/<X>/events/
  • Brouillon de réponse créé (create_draft, jamais send_email)
  • /documente invoqué automatiquement → re-synthèse Quick + Détails
  • Cascade vers linked_subjects (1 niveau)
  • Transitions seed→debating et debating→tentative appliquées
  • Commit + push

Quand tu lances /documente

  • Capture la conversation (si décision tranchée détectée) → fichiers discussions/ + decisions/
  • Invoque forge_engine.py (Python)
  • Régénère ## Quick + ## Détails en préservant les sections custom
  • Applique transitions auto (max 2 itérations chaînées)
  • Cascade horizontale vers linked_subjects
  • Diff affiché + commit + push (transparent)

Cohérence permanente

  • last_event toujours à jour (pas de stagnation surprise)
  • ## Quick reflète l'état réel (pas figé à seed)
  • Stats agrégées des supplier permanents recalculées à chaque cascade
  • Liens hétérogènes (supplier:weifang vs supplier-weifang) résolus via heuristique tolérante

🖐 Ce que tu fais MANUELLEMENT

Création (rare et déléguée)

Depuis v2.1 (2026-05-04) : tu n'as quasi-jamais à invoquer /subject-create ou /subject-create-type directement. C'est /documente qui les invoque automatiquement (création paresseuse).

  • Type : si tu lances /documente sur un subject de type inexistant, le skill te demande la confirmation puis lance /subject-create-type interactif.
  • Instance : si tu lances /documente sur un subject path inexistant (mais type connu), /subject-create est invoqué silencieusement (0 intervention).

Cas d'usage rare où invoquer directement : création préventive d'un type avant son premier usage, ou import depuis source externe.

Documentation (fréquent)

  • /documente <path> après une décision prise en session
  • /documente <path> après un travail manuel sur un subject (rafraîchir le Quick)

/control-tower appelle /documente pour toi. Mais si tu réponds à un email sans passer par /control-tower, c'est à toi de lancer /documente sinon le subject est aveugle.

Maturation γ (au cas par cas)

  • /stress-test <path> sur un subject en tentative pour le promouvoir
  • /compile-doctrine <path> quand conviction ≥ 80 et stress-test survived

Le scanner SessionStart te rappelle quand un subject est mûr ("doctrine non compilée" / "stress-test manquant").

Maintenance (occasionnel)

  • /subject-merge A B si tu détectes un doublon
  • Édition manuelle d'un MEMORY.md frontmatter (cas exceptionnels uniquement)
  • Archivage manuel à la clôture d'un cycle
⚠ Le piège à éviter

Si tu réponds à un mail directement depuis Mail/Outlook au lieu de passer par /control-tower, rien ne se passe côté subject pool. Le subject ne sait pas que tu as agi, et finira par apparaître en stagnation au scanner. Solution : soit toujours passer par /control-tower, soit lancer /documente manuellement après coup.

8.Compilation horizontale (la cascade)

Quand /documente tourne sur un subject racine, il propage la mise à jour sur 1 niveau strict à tous ses linked_subjects :

Sur le subject racine (verticale)

  • ✓ last_event recalculé
  • ✓ ## Quick régénéré (depuis events + analyses + discussions + decisions)
  • ✓ ## Détails régénéré (préserve sections custom)
  • ✓ Transitions γ auto appliquées
  • ✓ conviction bumpée si applicable

Sur les linked_subjects (horizontale)

  • ✓ last_event.type: cascaded_from_<root> avec ref vers l'event déclencheur
  • ✓ Stats agrégées recalculées (total_orders, total_amount_usd, etc.)
  • ✓ ## Quick régénéré pour intégrer la nouvelle activité
  • ✗ ## Détails NON modifié (préservé pour invocation directe)
  • ✓ Transitions γ auto si conditions remplies
Pourquoi 1 niveau strict

Une cascade récursive serait gourmande (un supplier permanent peut avoir 8 orders, qui pointent chacun vers d'autres subjects, etc.). On limite à 1 niveau pour rester sous 30s par invocation. Si un subject central a besoin d'une cascade plus profonde, tu peux invoquer /documente directement sur lui — chaque enfant déjà touché aura son Quick à jour, le parent re-synthétisé propagera à son tour.

Résolution des linked_subjects

Le format dans le frontmatter peut varier — le moteur résout via heuristique tolérante :

  1. Slug exact → <parent>/<slug>/MEMORY.md
  2. Format <type>:<name> → <parent>/<type>-<name>/MEMORY.md
  3. Format <type>:<name> → <parent>/<name>/MEMORY.md avec vérif type: dans frontmatter
  4. Recherche globale par name: dans tous les MEMORY.md
  5. Non résolu → warning, pas une erreur (la cascade continue sur les autres liens)

11.Troubleshooting

Mon subject reste en seed alors qu'il y a des events

Cause : /documente n'a pas été invoqué depuis l'ajout de l'event.

Solution : /documente <path> manuellement. Le chaînage seed→debating s'appliquera (≥1 event suffit).

Le scanner alerte "stagnation > 30j"

Cause : last_event.date est plus vieux que 30j et le subject est en seed | debating | tentative.

Solution : soit relancer un /documente (qui MAJ last_event depuis les fichiers existants), soit ajouter un event si rien ne s'est passé, soit archiver si le sujet est mort.

Le scanner alerte "doctrine non compilée"

Cause : forging_state: doctrine + conviction ≥ 80 mais compiled_artifacts: [].

Solution : /compile-doctrine <path> pour générer l'artefact. Skip de cette étape = le subject pool reste un wiki.

Une cascade donne un warning "linked_subject non résolu"

Cause : un linked_subjects: foo ne matche aucun MEMORY.md via les 4 heuristiques.

Solution : vérifier l'orthographe, créer le subject manquant via /subject-create, ou retirer la référence si elle est obsolète.

Le ## Quick régénéré écrase une section custom

Cause : la section custom était dans une zone considérée comme "narrative principale" par /documente.

Solution : déplacer la section custom dans le ## Détails sous une sous-section nommée (ex: ### Notes libres) — ces sous-sections sont préservées explicitement.

Le commit /documente échoue avec "rejected (fetch first)"

Cause : la remote a évolué depuis ton dernier pull.

Solution : git pull --rebase origin main puis git push. Le commit local reste intact.
